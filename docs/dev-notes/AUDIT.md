# AUDIT.md — Независимый аудит Steam Torrent Finder

# Executive Summary

MV3-расширение: content script вставляет кнопку на страницу игры Steam, поиск идёт параллельно по 5 встроенным трекерам + пользовательским «кастомным» через порт к service worker; результаты стримятся в боковую панель с табами/аккордеоном версий; настройки (папки, кастомные трекеры, RU/EN) — в popup через `chrome.storage.sync`.

Проект написан думающим разработчиком: есть потоковая передача результатов, эпочная защита от гонок, watchdog/stall-таймеры, экранирование в большинстве мест, санитизация storage. Но найдены две реальные security-проблемы (XSS через неэкранированные href с данными чужих сайтов; куки браузера, отправляемые с каждым fetch на произвольные сайты), системная лишняя нагрузка (ретраи на честно пустых результатах, до 15 fetch на TPB), ранний watchdog, рассинхронизированные дефолты в трёх файлах и парсер кастомных трекеров, отбрасывающий относительные ссылки (0 результатов на многих валидных сайтах).

Rewrite не требуется. ~15 локальных правок превращают MVP в устойчивый продукт.

# Critical Issues

## CR-01 — HTML-инъекция в атрибуты href/magnet из данных скрейпинга (XSS)

**Severity:** CRITICAL
**Area:** Security / DOM
**Location:** `content.js:469` (`href="${r.magnet}"`), `content.js:471`, `content.js:476` (`href="${r.detailUrl}"`), `content.js:493` (`fixCard`, `href="${d}"`)
**Problem:** `r.magnet` и `r.detailUrl` вставляются в HTML без `escapeHtml`. Значения приходят из background, где вырезаны regex-ами из HTML чужих сайтов и прогнаны через `decodeEntities()` (`background.js:79-87`), разворачивающую `&quot;` → `"`. Выборочные regex-ы вида `/href="(magnet:\?xt=urn:btih:[^"]+)"/i` не останавливаются на `&quot;` (это текст, а не символ `"`), значит закодированная кавычка проходит в значение целиком и разворачивается уже при рендере в content script.
**Why it matters:** Классический разрыв атрибута: рендер `href="magnet:...&quot; onmouseover=&quot;..."` даёт `href="..." onmouseover="..."` — обработчики атрибутов исполняются в контексте страницы Steam. Источник данных — третьи стороны (магниты/ссылки релизов, названия), а для кастомных трекеров — произвольные сайты, подключённые пользователем. Реальный вектор, не теоретический.
**How to reproduce:** Кастомный трекер, страница которого содержит `<a href="magnet:?xt=urn:btih:AAAA&dn=foo&quot; onmouseover=&quot;alert(document.domain)">...` → модалка рендерит строку с живым обработчиком.
**Recommended solution:**
- в `versionRow`/`fixCard` обернуть в `escapeHtml()` все интерполяции в атрибутах (`r.magnet`, `r.detailUrl`);
- на слое background — жёсткая валидация магнита (`^magnet:\?xt=urn:btih:([a-fA-F0-9]{40}|[A-Z2-7]{32})` + Whitelisted параметры) и `detailUrl` через `new URL()` с whitelist протоколов (http/https); невалидное → `magnet = null` (строка отрисуется ссылкой «детали»/прочерком).
**Risk:** Низкий. Возможен отказ от редких нестандартных магнитов.
**Priority:** P0 (первая правка)

## CR-02 — `<all_urls>` + `credentials:'include'` на все запросы: куки пользователя уходят произвольным сайтам

**Severity:** CRITICAL
**Area:** Security / Permissions / Fetch
**Location:** `manifest.json:7` (`host_permissions: ["<all_urls>"]`), `background.js:28` (дефолт `credentials:'include'` в `fetchWithTimeout`), `background.js:596-649` (`customParser` — fetch любого пользовательского URL)
**Problem:** Каждый fetch — ко всем трекерам, зеркалам и произвольным страницам кастомных трекеров — идёт с браузерными куками пользователя. Для Rutracker это осознанная фича (поддержка логина), но настройка размазана на все запросы: любые чужие сайты получают аутентифицированные запросы от имени пользователя и персонализированный контент, который потом парсится и показывается.
**Why it matters:** Пользователи подключают кастомные трекеры «по ссылке из forum-тредов» — расширение автоматически становится authentication-proxy для произвольных доменов; куки уходят на фишинговые/трекинговые ресурсы.
**How to reproduce:** DevTools на service worker: любой fetch несёт Cookie на удалённый хост (зеркала TPB, 1337x, произвольный кастомный).
**Recommended solution:** `fetchWithTimeout(url, ms, {credentials})` — credentials параметром; `include` только для whitelist (rutracker.org, freetp.org, online-fix.me — где вход реально работает), `omit` — для зеркал TPB, apibay, 1337x и кастомных трекеров по умолчанию. `host_permissions` пока оставить `<all_urls>` (иначе fetch кастомных трекеров не пройдёт); переход на `optional_host_permissions` с выдачей при добавлении кастомного трекера — отдельный long-term шаг.
**Risk:** Средний: юзер, полагающийся на логин-куки для 1337x/freetp, потеряет часть результатов; нужен per-host флаг «отправлять куки».
**Priority:** P0

# Major Issues

## MJ-01 — Ретраи выполняются даже при честном пустом результате: 3× нагрузка, до минуты ожидания «ничего не найдено»

**Severity:** MAJOR
**Area:** Reliability / Performance / UX
**Location:** `background.js:674-688` (`runTracker`: `if (results && results.length) return results;` — пустой результат проходит в ретрай-цикл)
**Problem:** Пустой массив трактуется как «неудача», и трекер перезапускается до 3 раз с паузой 2.5 с. Для игр, которых физически нет на трекере — частый кейс — каждая попытка повторно тянет все страницы: 1337x — до 12 fetch (2 хоста × 2 URL × 3 попытки), freetp — 3×(поиск + до 5 страниц релизов). Итог — до 60-90 c «Ищем…» перед «ничего не найдено».
**Why it matters:** Пользовательский опыт и лишняя сеть; риск rate-limit на трекерах.
**How to reproduce:** Поиск экзотической игры с включёнными 1337x + freetp; «Ничего не найдено» приходит через ~минуту.
**Recommended solution:** Различение «честно пусто» и «неизвестности»: парсер возвращает `[]` без ретрая, если видна живая разметка без результатов (apibay — `[{id:"0"…}]`, TPB HTML — `#searchResult` без магнитов, 1337x — `coll-1` без строк, freetp/online-fix — маркер страницы результатов). Если маркер разметки ОТСУТСТВУЕТ — трекер возвращает ошибку «разметка изменилась», а не пусто, иначе молчаливая поломка сайта станет ложно-пустым ответом. Ретраить только исключения (сеть/HTTP), максимум 2 попытки.
**Risk:** Низкий-средний: важно, чтобы маркеры разметки присутствовали в каждом парсере.
**Priority:** P1

## MJ-02 — Watchdog 75 c короче worst-case легального поиска → законный поиск прерывается ложным timeout

**Severity:** MAJOR
**Area:** Reliability
**Location:** `content.js:249-256` (watchdog 75000 мс) vs `background.js:674-688` (3 попытки × fetch 12-15 с + паузы 2.5 с + до 5 enrich-фетчей по 12 с)
**Problem:** Worst-case трекера (freetp, 1337x с ретраями и enrich-приставкой) — 80-90+ c. Watchdog на 75 c покажет «Поиск занял слишком много времени», пока трекер честно работает, и `stopSearch()` убьёт порт вместе с ещё приходящими результатами.
**Why it matters:** На слабом интернете ложная ошибка и потеря результатов, которые пришли бы позже.
**How to reproduce:** DevTools → Slow 3G, поиск с freetp+x1337: через ~75 c открывается «timeout», а Network продолжает грузить страницы.
**Recommended solution:** Activity-based watchdog: продлевать таймер на каждый входящий `trackerResult`/`started`; жёсткий абсолютный потолок (например, 120 c) оставить как предохранитель.
**Risk:** Нулевой.
**Priority:** P1

## MJ-03 — Полный innerHTML-re-render активной вкладки на каждый `trackerResult` + повторное навешивание слушателей

**Severity:** MAJOR
**Area:** Performance
**Location:** `content.js:297-315` (`renderIncremental`), `content.js:500-516` (`bindAccordion`), `content.js:519-544` (`bindTabs`)
**Problem:** Каждый промежуточный результат трекера перестраивает HTML всех групп активной вкладки и заново вешает обработчики. С M трекерами — M полных rebuild; открытый аккордеон восстанавливается через `openGroups Set` (механизм хороший), но пересборка дорогая и лишняя.
**Why it matters:** При 6-10 трекерах поздняя стадия поиска тормозит и визуально дёргается.
**How to reproduce:** Включить 8+ трекеров; в Performance-профиле — серия больших Layout/RecalcStyle на каждый `trackerResult`.
**Recommended solution:** Изоляция узла на трекер (`<div data-tracker="key">`), обновление только своего узла по приходу своего результата; события — делегирование кликов на контейнер `#stf-groups`.
**Risk:** Низкий; логика `openGroups` переносится без изменений.
**Priority:** P1

## MJ-04 — Дефолтные наборы задублированы в 3 файлах и уже разъехались

**Severity:** MAJOR (maintainability)
**Area:** Architecture
**Location:** `background.js:7-21` (DEFAULT_SETTINGS с enabled/color/group), `content.js:633-668` (TRACKER_COLORS + DEFAULT_TRACKERS_UI/DEFAULT_GROUPS_UI), `popup.js:5-11` (BUILTIN_META)
**Problem:** Одинаковая структура (списки трекеров, групп, дефолтных раскладок) воспроизводится в трёх местах с расхождениями. Content script знает имя/цвет встроенных только через свой fallback; popup делает собственную миграцию; background имеет своё мнение о дефолтах. Добавление нового трекера требует правок в 3 файлах.
**Why it matters:** Главный источник будущих рассинхронизаций: первый же внешний PR «добавить трекер» придёт в один файл и даст частично работающий трекер.
**How to reproduce:** Вручную добавить в storage ключ трекера без searchUrl — popup показывает, content не рендерит мету, background падает с «шаблон без {q}».
**Recommended solution:** Единый `common.js` с `DEFAULT_TRACKERS`, `DEFAULT_GROUPS`, `BUILTIN_META`, `TRACKER_COLORS`; подключение как `<script>` в popup/content и через `importScripts`/module в SW.
**Risk:** Низкий (рефактор), требует порядка загрузки.
**Priority:** P2

## MJ-05 — `customParser` отбрасывает относительные ссылки → для многих сайтов всегда 0 результатов

**Severity:** MAJOR
**Area:** Feature robustness
**Location:** `background.js:611` (regex требует `https?://` в href), `background.js:616` (фильтр same-origin через `startsWith(origin)`)
**Problem:** Парсер кастомных трекеров собирает только абсолютные ссылки того же origin. Многие DLE/WordPress-движки отдают `<a href="/index.php?newsid=...">` — главные ссылки на релизы — и теряются; их поиск всегда даёт «0».
**Why it matters:** Кастомные трекеры — ключевая фича (online-fix-сервисы почти все с relative-ссылками).
**How to reproduce:** Добавить трекер с relative-ссылками; поиск существующей игры — пусто при наличии релевантных ссылок в HTML.
**Recommended solution:** Резолвить через `new URL(href, baseUrl)`; same-origin оставить. Заодно поддержать магнит прямо в списке результатов, без второй фазы grabMagnet.
**Risk:** Низкий.
**Priority:** P1

## MJ-06 — Три почти идентичных enrich-функции (copy-paste)

**Severity:** MAJOR (maintainability)
**Area:** Architecture
**Location:** `background.js:537-557` (x1337Enrich), `560-588` (freetpEnrich), `634-646` (grabMagnet в customParser)
**Problem:** Три копии логики «fetch страницы релиза → вытащить магнит/дату/размер», различаются только кодировкой и набором regex; любой фикс трекера нужно вносить в 2-3 места.
**Recommended solution:** Общий `fetchPage(url, {enc})` + декларативные экстракторы; `enrich(results, topN, {enc, extractors})`.
**Risk:** Низкий, рефактор с regression-тестами на фикстурах.
**Priority:** P2

# Performance Issues

## PF-01 — TPB HTML: до 15 лишних fetch (3 попытки × 5 зеркал) за один поиск

**Severity:** MAJOR
**Location:** `background.js:272-297` (`piratebayHtml` — 5 зеркал × `Promise.any`, × до 3 попыток `runTracker`) + apibay fallback
**Problem:** Даже после успеха первого зеркала остальные продолжают грузить страницы (нет abort для проигравших fetch); с ретраями — до 15 запросов с credentials.
**Solution:** (a) кэш «живое зеркало» и повторная попытка сначала по нему; (b) общий AbortController-набор, обрывающий проигравшие зеркала после `Promise.any`; (c) не ретраить зеркальный HTML, если apibay уже дал результат.
**Risk:** Низкий. **Priority:** P1

## PF-02 — MutationObserver на всё body/subtree с 2× querySelector в каждом вызове

**Severity:** MINOR
**Location:** `content.js:737-742`
**Problem:** Callback срабатывает на каждое DOM-изменение Steam (сотни в минуту), включая собственные рендеры модалки.
**Solution:** Debounce ≈300 мс или сузить наблюдение.
**Risk:** Нулевой. **Priority:** P3

## PF-03 — Слушатели аккордеона/табов навешиваются заново на каждом рендере

**Severity:** MINOR (решается вместе с MJ-03)
**Location:** `content.js:500-516`, `519-544`
**Solution:** Делегирование кликов на контейнер.
**Priority:** P1 (совместно с MJ-03)

## Краткие ответы

1. **Исправить в первую очередь:** CR-01 (экранирование href/магнитов + валидация), CR-02 (credentials по whitelist), MJ-01 (не ретраить честно пустые результаты).
2. **Оставить как есть:** потоковый протокол (порт/эпохи/safePost/finally done), алгоритмы релевантности и группировки, встроенные парсеры (только точечные фиксы), санитизация папок, дизайн панели.
3. **Наибольший прирост качества:** MJ-01 + MJ-03/PF-03 (инкрементальный рендер + делегирование) + MJ-04 (единые дефолты) — скорость, надёжность и дешёвое сопровождение.
4. **Наиболее рискованные изменения:** MJ-04 (миграция дефолтов в общий модуль — риск рассинхронизации при переезде) и MJ-01 (различение «честно пусто» и «разметка сломана» — нужны явные маркеры в каждом парсере, иначе молчаливая поломка трекера станет ложно-пустым ответом).
5. **Обязательные тесты после реализации:** (a) happy path по всем 5 встроенным трекерам на известной игре (мок-фикстуры); (b) XSS-вектор `&quot;` в магнит/URL не исполняется; (c) повторный клик/закрытие панели в момент поиска — нет висящих таймеров и сообщений старой эпохи; (d) popup: создание/удаление/драг папок → сохранение → модалка показывает правильные вкладки; (e) кастомный трекер с относительными ссылками находит результаты (MJ-05); (f) watchdog не срабатывает раньше фактического окончания легального поиска на медленном соединении (MJ-02); (g) честно пустой результат приходит заметно быстрее (MJ-01 — время до «ничего не найдено»).
